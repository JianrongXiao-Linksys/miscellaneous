1. TEST OBJECTIVE

The first of your two options: overall endurance and stability across repeated factory resets, including CNSS/WLAN bring-up. It is not a study of how individual modules or drivers load — we never load or unload drivers by hand.

The loop mirrors our manufacturing-line sequence: factory reset through the device management API -> wait for the unit to drop off -> wait for ping -> 10 s grace -> check the factory status endpoint and a management API request on port 80 -> immediately trigger the next reset. 15 to 30 cycles per run.

The important timing detail: we deliberately do not wait for initialization to complete, so the next reset can arrive while CNSS and WLAN bring-up are still in progress. That is intentional, because it is what the production station does.

Two observations that may help you scope the panic:

  - Both panics occurred on boots where the configuration tree was empty or unreadable ("uci: Entry not found", "Region= not found in list.", empty SKU). With no valid region/SKU/board parameters, board-data and regulatory selection have nothing valid to select, the CNSS error path is entered, and CNSS_ASSERT() fires. The reset loop is only the trigger; the defect is the assert on a recoverable path.
  - The second panic is reached from userspace: nl80211_vendor_cmd -> wlan_cfg80211_set_wificonfiguration -> wlan_cfg80211_set_params -> ol_ath_ucfg_setparam -> ol_ath_check_and_start_target -> ol_ath_target_start -> ol_ath_soc_start -> __cnss_subsystem_get -> BUG() at main.c:3609. A userspace configuration command should not be able to panic the kernel.
