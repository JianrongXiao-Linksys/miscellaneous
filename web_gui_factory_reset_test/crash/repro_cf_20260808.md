# CF firmware reproduces the same kernel panic — 2026-08-08

Run to confirm the panic is **not** specific to the M60PW-HK build, after rolling
back `cnss2.skip_cnss=1`. Reproduced on **iteration 2**, same as on the PW build.

| Model | M60CF-EU (re-SKU'd from M60PW-HK, same physical board) |
| Firmware | 1.2.3.26080709, `build_target=CF`, built 2026-08-07T16:23:17Z |
| SDK / kernel | `spf12.5_csu1`, 5.4.213 |
| Bootargs | `console=ttyMSM0,115200n8 cnss2.enable_mlo_support=1` — **skip_cnss removed** |

instance** — I had earlier flagged it as wrong based on the -ENOENT capture alone.
Both values occur; that is itself a finding, since -ENOMEM points at allocation
pressure during Q6 load rather than a missing firmware path.

## Conclusions

1. **The panic is not PW-specific.** CF 1.2.3.26080709 reproduces it on the same
   iteration (#2) with the same aggressive reset timing.
2. **It is not caused by our debug boot argument** — `skip_cnss` was fully rolled
   back and verified absent before the run.
3. **`skip_cnss=1` masks it**, consistent with the earlier 15/15 clean run: with
   CNSS probe skipped the driver never attaches, so `rproc_boot()` is never called.
4. **The `rproc_boot()` error value varies** (-ENOMEM here, -ENOENT before), so a
   single-cause theory based on the firmware-path lookup alone is insufficient.
5. **The "web refused" failure at iteration 2 is a symptom of the panic**, not the
   lighttpd `validate_conf` issue — the board was rebooting, not serving. The two
   defects are distinct and must not be conflated in the #451 analysis.
